# PetFlow 제품 계약

이 문서는 PetFlow의 현재 제품 판단 기준이다. 오래됐다는 이유만으로 요구사항,
문서, 화면, 데이터 모델을 사실로 간주하지 않는다. 사용자 행동과 매출 검증 결과가
기존 문서와 충돌하면 근거를 확인하고 이 계약부터 고친다.

## 한 문장 정의

PetFlow는 병원에 가기 직전 보호자가 반려동물의 변화를 한 줄과 사진으로 남기고,
자신이 소유한 관찰 기록을 수의사에게 바로 보여줄 사실 중심 전달본으로 정리하는
서비스다.

PetFlow와 AI는 진단하거나 처방하지 않는다. 보호자와 수의사 사이에서 반복되는
설명을 줄이는 기록·정리 도구다.

## 현재 사업 단계

지금의 목표는 꾸준한 건강관리 습관이나 범용 플랫폼을 만드는 것이 아니다. 병원
방문이 임박한 보호자가 Android와 iOS 앱에서 3분 안에 상황을 기록하고, 전달본을
만들어 공유하고, 필요하면 스토어에서 1회 결제하는 흐름을 증명하는 단계다.

- 최우선 결과는 다운로드 수가 아니라 실제 스토어 결제 1건과 반복 구매 신호다.
- 일일 활성 사용자나 연속 기록보다 `병원 준비 시작 → 전달본 생성 → 공유` 완료율과
  완료 시간을 먼저 본다.
- 기능은 `기록 부담 감소`, `병원 전달 가치`, `유료 전환` 중 하나에 직접 기여해야 한다.
- 웹 사용을 핵심 흐름의 전제로 두지 않는다.
- 병원 대시보드, 범용 BeFlow, 광고, 커뮤니티는 첫 유료 흐름을 늦추면 만들지 않는다.
- 새 기능보다 첫 실행부터 전달본 공유까지 걸린 시간, 생성률, 공유율, 결제
  전환율을 먼저 본다.

## 첫 고객과 약속

- 첫 고객은 반려동물의 달라진 사실이 사진·메모·기억에 흩어져 있고, 오늘부터
  7일 안에 병원 방문을 앞둔 보호자다.
- 반복 증상이나 투약으로 병원을 다시 찾는 보호자는 가입 조건이 아니라 다음 방문의
  재사용과 재구매를 검증할 핵심 하위 집단이다.
- 첫 사용자와 지불자는 보호자다. 수의사는 전달본을 받는 사람이며 가치 검증자다.
  첫 매출이 검증되기 전에는 병원 계정이나 대시보드를 핵심 흐름의 전제로 만들지 않는다.
- 사용자에게 하는 약속은 `언제부터 무엇이 달라졌는지 다시 정리하고 설명하는 시간을
  줄인다`다. 진단 정확도 향상이나 진료 결과 개선을 약속하지 않는다.
- 기능 수나 AI 사용 자체를 차별점으로 삼지 않는다. 휴대전화 메모, 사진첩, 메신저,
  달력과 범용 AI를 함께 쓰는 것보다 더 적은 입력으로 병원에 보여줄 사실 전달본을
  만드는 경험이 명확히 빨라야 한다.

## 유료 가치 검증

현재 단계에서는 일일 활성 사용자, 연속 기록과 일반적인 7일 유지율보다 아래 순서의
행동을 우선 확인한다.

1. 병원 준비를 시작한 사용자가 전달본을 생성하고 공유했는가
2. 공유한 전달본을 실제 병원에서 보여줬는가
3. 언제부터 무엇이 달라졌는지 설명하는 부담이나 누락이 줄었는가
4. 병원에서 들은 내용을 다음 방문을 위해 다시 남겼는가
5. 다음 병원 방문에서 기존 기록을 재사용했는가
6. 무료 사용 뒤 1회 이용권을 구매하고 다시 구매했는가

실사용 확인이 필요하면 병원 방문 뒤 선택형 한 질문으로만 받고 기록·공유·결제를
막지 않는다. 구독, B2B 판매와 병원 연동은 반복 구매와 병원 실사용 신호가 확인된
뒤에 판단한다.

## 획득과 유지 LOOP

1. 병원 방문이 임박한 보호자가 반복 설명을 줄이기 위해 앱을 설치한다.
2. 이름·종류와 달라진 점 한 줄, 필요할 때 사진을 남겨 첫 전달본을 만든다.
3. 병원에서 실제로 들은 내용은 보호자 보고 정보로 한 줄만 이어둔다.
4. 새 변화나 다음 병원 방문 때는 달라진 사실만 더하고, 이전 기록과 병원 안내는
   같은 흐름의 다음 전달본에 자동으로 포함한다.
5. 첫 무료 전달본으로 가치를 확인한 뒤 새로운 병원 전달본이 필요한 순간에 1회
   이용권을 다시 구매한다.

유지는 출석, 연속 기록, 강제 알림이나 수동 흐름 마무리로 만들지 않는다. 사용자가
소유한 사실 기록이 쌓일수록 다음 설명 시간이 줄어드는 가치로 돌아오게 한다. 조회,
수정, 삭제와 기본 내보내기를 막아 이탈을 어렵게 만드는 방식은 사용하지 않는다.

## 핵심 흐름

1. 보호자는 이름과 종류만으로 반려동물을 고르거나 등록한다.
2. 병원에서 설명할 변화와 시점을 한 줄로 쓰고 사진·영상을 필요할 때 더한다.
3. 앱은 선택한 증상에만 수의사가 자주 묻는 최소 사실 태그를 보여주고,
   식욕·활력·반복 변화와 함께 선택적으로 구조화한다.
4. 기존 기록이 있으면 보호자가 병원에 가져갈 날짜나 기간만 고른다.
5. 기본 사실 요약을 확인하고 필요하면 병원 전달본을 생성·공유한다.
6. 병원에서 실제로 받은 설명은 보호자 보고 정보로 이어서 남긴다.

사용자 화면에는 `SOAP`, `episode`, `progress log` 같은 내부 용어를 강요하지
않는다. `기록`, `건강 흐름`, `병원 전달본`처럼 행동이 분명한 말만 쓴다.

## 데이터 주권

- 원문 관찰과 첨부 자료는 보호자 계정과 한 반려동물에 귀속한다.
- 보호자는 원문을 조회·수정·삭제하고 계정 전체를 탈퇴할 수 있다.
- 원문, 앱의 결정론적 정리, AI 초안, 보호자가 옮긴 병원 안내를 분리한다.
- AI가 만든 문장은 `unreviewed` 초안이며 수의사 확인 정보로 표시하지 않는다.
- 병원 안내는 기본적으로 `owner` / `user_reported`다. 실제 병원 확인 절차가
  없는 한 `expert_confirmed`로 바꾸지 않는다.
- 사용자 기록을 외부 분석 도구나 모델 학습에 기본 제공하지 않는다.

## 보안 기본선

- 브라우저와 앱이 보낸 사용자 ID, 반려동물 ID, 파일 경로, 테스트 플래그,
  결제 상태를 신뢰하지 않는다.
- 모든 비공개 API는 서버가 액세스 토큰을 검증하고 데이터 소유권을 다시 확인한다.
- RLS와 외래 키로 계정, 반려동물, 기록의 소유 관계를 데이터베이스에서도 강제한다.
- OpenAI 키와 Supabase service role 키는 서버에만 둔다.
- AI 호출 전 서버에서 소유권과 사용 권한을 원자적으로 예약한다.
- 업로드 경로는 서버가 발급한다. 파일은 비공개 버킷에 두고 짧은 서명 URL로 읽는다.
- 요청 크기, 문자열 길이, 허용 값, 파일 형식과 크기를 서버에서 제한한다.
- 배포 검증용 공개 우회 헤더나 익명 더미 저장 경로를 만들지 않는다.
- 로그에는 액세스 토큰, 원문 메모, 서명 URL, 비밀키를 남기지 않는다.

## 앱 우선 계약

- 보호자의 핵심 행동은 Android와 iOS 앱 안에서 끝나야 한다.
- 웹은 운영, 개인정보 안내, 계정 삭제 안내와 보조 접근 경로다. 핵심 유료 흐름의
  전제 조건으로 두지 않는다.
- 한 화면에서는 한 가지 주요 행동만 요청한다.
- 정상 상태는 한 번에 저장하고, 상세 입력은 필요할 때만 보여 준다.
- 같은 정보를 다시 묻지 않는다. 직접 `흐름 마무리`나 정해진 날짜의 경과 입력을
  요구하지 않는다.
- 긴 설명은 짧은 튜토리얼이나 도움말로 옮기고 반복 화면에는 남기지 않는다.

보안은 제품의 목적이 아니라 반드시 지켜야 하는 기본 위생이다. 보안을 이유로
사용자 입력을 늘리거나 핵심 유료 검증을 불필요하게 늦추지 않는다.

## 첫 유료 검증

- 일상 기록 저장과 결정론적 안전 분류에는 생성형 AI를 호출하지 않는다.
- AI는 사용자가 고른 여러 기록을 수의사가 읽기 쉬운 사실 초안으로 정리할 때만
  사용한다.
- 병원 전달본의 중심은 보호자가 남긴 원문 한 줄, 관찰 시점, 선택한 사실과
  첨부 자료다. 체크스코어와 앱의 안전 단계는 보호자 안내에만 사용하고 수의사에게
  전달하는 객관적 사실처럼 섞지 않는다.
- 저장된 기록은 실제 날짜순으로 보여준다. 내부 호환용 3·7·14일 구간이나 예정
  경과 시점을 사용자에게 문진 항목 또는 병원용 사실로 노출하지 않는다.
- 증상별 사전 문진은 보호자가 선택한 사실만 전달하고, 답하지 않은 항목을
  추정하거나 이미 답한 내용을 다시 질문으로 만들지 않는다.
- 사전 문진은 횟수·상황·부위·눈에 보이는 양상처럼 보호자가 바로 관찰할 수 있고
  진료실의 첫 질문을 줄이는 사실만 다룬다. 증상명 반복, 일반적인 당부, 원인 추정,
  보호자가 판단할 수 없는 의학적 감별 질문은 만들지 않는다.
- 원문 기록의 조회·수정·삭제와 기본 내보내기는 결제 여부와 분리한다.
- 첫 상품은 `병원 전달본 1회 이용권`으로 한다. 전달본은 AI가 선택한 기록을
  사실 중심으로 정리한다. 구독은 반복 구매 신호가
  확인되기 전에는 도입하지 않는다.
- 기본 가설은 첫 병원 전달본 1회 무료, 이후 1회 이용권 1,900원이다. 스토어 가격
  구간이 다르면 가장 가까운 가격을 사용하고 실제 전환율로 조정한다.
- 모바일 결제는 Apple·Google 인앱결제만 사용한다. 앱에서 웹 결제로 유도하거나
  참여코드·수동 권한 부여로 디지털 기능을 우회 판매하지 않는다.
- 웹은 결제를 제공하지 않는다. 모바일 구매는 Supabase 사용자 UUID에 연결해
  iOS와 Android에서 같은 계정의 서버 이용권으로 확인한다.
- Apple·Google 구매는 RevenueCat의 검증된 거래 내역과 서버 원장을 대조한다.
  서버 이용권이 확정된 경우에만 유료 AI 생성을 예약한다.
- 결제 화면에는 생성 결과의 범위, 진단이 아니라는 점, 남은 이용 횟수와 복원
  방법을 짧게 표시한다.
- 첫 매출 실험의 핵심 지표는 `요약 대상 도달`, `결제 화면 진입`, `구매 완료`,
  `요약 생성`, `공유`, `재구매`다.
- 스토어 설명과 심사 메모는 현재 제출 빌드에서 실제로 구매 가능한 상품만 말한다.

## 안전 경계

- 질병명 확정, 처방, 약명, 용량, 치료 권고를 생성하지 않는다.
- 응급 징후는 결정론적 규칙으로만 안내하고 결과를 진단처럼 표현하지 않는다.
- 사진과 영상은 보관·공유하되 별도 동의와 안전 검증 전에는 AI가 판독하지 않는다.
- AI 보고서는 입력된 사실만 사용하고 누락 정보와 불확실성을 명시한다.
- 모든 병원 전달 문서에 진단 대체물이 아니라는 점을 짧고 분명하게 표시한다.

## 현재 우선순위

1. 병원 가기 직전 한 줄·사진 입력부터 전달본 공유까지 3분 안에 완료
2. Google·Apple 로그인, 계정 연결·로그아웃·탈퇴의 안정성
3. 선택한 날짜·기간의 사실 기록으로 병원 전달본 생성·공유
4. 첫 무료 병원 전달본과 1회 이용권의 서버 검증 entitlement
5. 실제 스토어 결제 1건과 재구매 가능성 확인
6. 공유 결과가 보호자의 설명 시간과 수의사의 문진 부담을 줄이는지 확인

병원 대시보드, EMR 양방향 연동, 보험, 범용 BeFlow 화면, 자체 모델 학습은 위
흐름과 첫 유료 전환이 검증된 뒤 다시 판단한다.
